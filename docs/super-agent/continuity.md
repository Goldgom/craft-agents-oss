# 任务持续性与执行效率

服务自更新、MCP 重载与异常退出的统一自动续做方案见 [重启恢复设计](../restart-recovery-design.md)。该方案尚未接入运行时；本文以下描述现有行为。

现有 Microsoft Agent Framework 工作流继续连接意图、编排与工作节点。宿主持久化执行状态并检查派工条件；模型通过隐藏提示词获取职责、共享数据索引与工具协议。子节点可见请求仍是上游传入的原始任务或消息，续做信息进入隐藏上下文。

## 目标与验收

- 意图节点创建稳定目标 ID；更新已有要求提交 `intent.id` 和 `expectedRevision`，保留仍有效的要求。
- 编排节点用 `goalId` 关联计划和任务；任务的 `goalCriteria` 是目标验收条件的零基索引。
- 用户更新目标后，旧任务的验收失效，已完成计划重新打开。编排节点须刷新计划契约，再安排当前版本的工作；宿主阻止旧契约派工、续做和验收。
- 默认由执行者自检，声明验收条件不会开启强制复核或要求额外验收记录。只有用户明确要求独立复核时，才设置 `requiresIndependentReview=true`，安排 `reviewOf` 任务并记录验收。
- 所有关联计划完成、当前版本的成功任务覆盖每一项目标验收条件后，目标才标记为已交付。明确要求复核的任务须通过验收；失败、被拒绝、过期或存在未知操作的结果不能用于完成计划。轮次结束只表示提交结果，后台仍须依据真实证据判断用户要求是否满足。
- 已提交前置任务因复核、过期证据或未知操作导致队列无法推进时，宿主向后台提交一次具体诊断，不等待空闲自检；同一证据状态去重，避免重复付费轮询。

## 检查点与条件等待

排队任务在派工前检查目标版本、前置任务和计划。目标过期、目标或前置任务已取消、前置任务缺失等无法继续的旧任务会自动取消，保留已有结果，并通知编排节点按最新要求重新规划。内部核验、依赖修复与执行问题由 AI 自动处理；只有必须由人提供的信息、授权或决定才等待用户。等待前置任务或计划解除内部阻碍的队列显示恢复状态，不要求用户点击检查。

内部问题显示“AI 自动核验与恢复”，无需用户操作；只有用户型阻碍显示受阻卡片和具体请求。卡片列出当前问题、已提交结果与登记产物、用户行动及系统下一步。原报告、操作 ID 和哈希放在默认折叠的技术详情中。已提交结果不等同于最终验收通过。计划与其排队任务合并展示，避免重复报告同一阻碍。用户请求不会因其他节点正在工作而被折叠隐藏。

编排设置计划为 `blocked` 时可提交结构化 `blocker`：系统问题用 `{ "kind": "system", "summary": "当前阻碍", "systemAction": "具体处理步骤与解除条件" }`；确需用户信息时用 `{ "kind": "user", "summary": "具体缺少什么", "userAction": "用户需提供的字段、文件或选择", "systemAction": "收到后如何继续" }`。用户型阻碍必须有非空具体行动，界面提供“补充信息”按钮定位输入框并保留已有草稿。旧报告根据真实操作与依赖状态展示；无法判断时让智能体明确解除条件，不猜测用户缺少什么。计划恢复或系统替换受阻原因时清除旧指导，避免显示过时要求。这些字段只用于说明状态，不扩大授权或改变验收规则。

活动工作节点使用 `mcp__session__super_agent_task`（`super_agent_task`）。宿主按当前会话、活动轮次和任务负责人校验每次更新。

```json
{
  "action": "checkpoint",
  "taskId": "build-report",
  "expectedRevision": 0,
  "completedSteps": ["输入已验证"],
  "nextStep": "生成报告并运行验证",
  "note": "输入版本及产物路径"
}
```

不能丢弃已完成步骤；重复检查点及仅修改备注不会增加阶段版本或重置无进展时间。未结算的副作用须先核验。更新检查点是模型声明的进展，宿主不据此认定业务结果正确。

缺少输入时先保存检查点，再提交 `action=wait`，包括 `taskId`、`reason` 和 `condition`，并结束本轮。条件支持：

| kind | 条件 |
| --- | --- |
| time | 达到毫秒时间戳 `notBefore` |
| board | `itemId` 的修订号超过 `afterRevision` |
| task | `taskId` 完成且满足依赖验收规则 |
| file | 目录内 `path` 存在，或内容与给定旧 `sha256` 不同 |

持续工作开启时，宿主每约 5 秒检查条件，无需轮询模型。条件满足后复用原任务 ID 和原始请求，从隐藏检查点继续。检查点没有推进时，自动续做受次数限制；保存新阶段或用户手动继续会重新开始计数。手动继续允许用户解除原等待，结果未知或脚本仍运行时仍禁止重复执行。

关闭服务会保存队列、检查点和中断证据，并尝试停止活动会话及受管脚本。下次启动只自动恢复已保存检查点、目标契约有效且无未确认操作或进程的失败任务。显式停止会清除检查点，防止后续条件或重启唤醒。没有检查点的中断任务保留失败记录供核查。

## 操作记录与未知结果

可能产生副作用的工具在派发前，必须等待操作记录保存成功。记录包含任务/轮次、阶段、工具、规范化参数的指纹和提供商调用 ID；不保存原始参数、凭据或工具结果正文。

`prepared → running → completed` 表示登记、启动和返回成功结果。连接中断、错误或未收到确定结果时保留 `unknown`，不自动重放。相同任务、阶段、工具和参数的重复操作被拦截；明确推进检查点后，可执行另一个独立步骤。未知操作继续占用其任务声明的写资源，读取验证任务可继续。

核验应分配给另一个工作节点，指令写明操作 ID、同一 `goalId` 与查询方法。核验节点可用 `action=get` 和原任务 ID 读取指令引用的操作记录及任务，不需要依赖原任务的验收；这不会授予修改原任务检查点的权限。可加 `operationId` 精确读取一项。返回的 `operationReceipts` 从原宿主会话读取对应调用的原参数 `inputJson` 与原结果 `result`，核对工作区、会话、调用 ID、工具名及已存 `resultHash`，不将正文复制到协调状态。每次最多读取 20 项，超限返回 `receiptsTruncated`，可逐项查询；单项输入和结果截断分别明确标记。缺失或哈希不符的回执不会作为可用证据返回，应再向原执行者索证。工具报错不能证明副作用未发生，真实回执仍须独立判断执行事实和影响。

核验节点先提交报告并结束本轮。证据任务成为 `completed` 且自身没有未知操作后，编排节点发送后续消息唤醒同一核验节点，再由该节点调用：

```json
{
  "action": "reconcile",
  "operationId": "op_example",
  "evidenceTaskId": "verify-receipt",
  "outcome": "completed",
  "note": "真实回执与核验结果的位置"
}
```

`outcome=not-executed` 表示核实未执行，允许后续重试。宿主验证证据任务的归属、关联和完成状态；外部事实仍依赖真实工具与报告。这是避免重复执行的记录机制，不是外部系统的 exactly-once 保证。

产出任务或验收证据有未结操作时，宿主拒绝 `accepted` 并返回具体操作 ID。编排优先安排核验或结果登记；通信预算耗尽不会转成用户求助。队列空闲时宿主自动选择另一个工作节点，创建同目标的独立核验任务；核验使用独立计划，不被原计划的内部阻碍拦住。证据完成后自动安排该节点调用 `reconcile`，再把结果交编排继续验收与后续工作。验收先于派工和消息执行，所以安排核验的动作块须省略受阻验收。

内部恢复在未开启持续工作时仍运行，也会处理重启后的旧受阻状态。核验任务及结果登记轮次的身份持久化，避免重复派工；相同未变化的证据只触发一次恢复复核，不无限重复付费模型调用。证据不足时保留未知状态，由团队查明缺口；只有缺口确实需要人提供信息、授权或决定时才列出具体用户请求。取消目标、任务或明确停止后不自动恢复；整体停止状态持久化，用户重新发起工作时解除。恢复不重放原操作、不自动猜测执行结果、不绕过现有权限和验收规则。

**完全控制继续跳过全部人工审批、Action Gates 与 Auto-review。**持久化、去重、资源互斥和未知结果核验不产生新审批；文件工具可直接访问工作目录内外的宿主路径，数据源、禁止规则和容器边界按当前执行策略生效。

## 回复重复与节点上下文恢复

节点间相同消息在仍排队或执行时合并；同一用户请求与证据状态下已经送达的相同消息也不再次唤醒节点。比较时统一空白与 Unicode 表示，新用户请求、任务结果、产物版本或工具状态变化后允许重新通知。纯收件确认，以及明确无需回复的停止通知产生的确认，不再触发编排汇总；新的错误、证据和有效动作仍正常交接。

意图与编排节点的隐藏状态提供近期已向用户展示的 `userReplies`，上下文更新后仍能对照已经交付的内容，仅转述新增成果或决策事项。后台相同答复在没有新证据时隐藏；连续两次被拦截则更换该节点的模型会话，下一轮从持久状态继续。

单次输出中大部分内容反复逐字重复时，宿主在应用该回复的控制动作前拒绝输出，并更换对应节点上下文。无未确认操作时最多自动续做一次，次数随队列持久化；新上下文仍重复则停止自动重试。存在未知操作时先核验，不自动重放。上下文更换保留其他节点、原任务、检查点、计划、产物及操作记录；旧会话保留用于读取原始工具回执。这与删除会话及检查点的完整节点重置不同。

检测针对明确的逐字重复，不能证明所有换措辞的重复都已消除；防止此类问题还依靠最新证据状态与已交付内容约束。

## 产物版本

工作节点以 `action=artifact` 登记 `taskId`、`id`、`path` 和可选 `description`。宿主验证目录边界，流式计算不超过 64 MB 的真实文件 SHA-256，并检查读取期间文件是否变化。

验证任务在启动时绑定依赖产物的哈希。验收时重新读取文件并核对注册版本和验证输入版本；产物变更或缺失使生产任务、消费者和传递依赖的旧验收失效，并重新打开已完成计划与目标。周期扫描先检查文件元数据，未变化的文件避免重复哈希；验收始终计算实际内容。哈希证明版本一致性，内容正确性由验证任务确认。

## 调度与开销

- 节点能力标签与任务 `requiredCapabilities` 决定匹配；指定不匹配节点会被拒绝。
- 每节点仍串行，连接预算在同一服务已加载的工作区之间累计；连接限额和每节点限额均需满足。每分钟限制统计模型轮次启动，不代表供应商所有内部 HTTP 请求。
- 新配置默认每连接并发 4、每分钟 60 轮、无进展提醒 15 分钟、自动续做 3 次。旧配置缺少 `execution` 时保留兼容的并发/速率上限。
- 计划优先级、等待时长与下游依赖数影响派工顺序。
- 相容的未启动编排结果汇总轮次合并；用户输入、脚本结果关联、重试轮次保留各自处理流程。
- 无进展提醒交编排节点检查活跃工具、进程和阻碍，不因安静而取消长计算；重复成功工具结果不刷新进展时间。同一停滞阶段只提醒一次。
- 共享板可按 `goalId`、`taskId`、`itemIds` 查询，并用 `offset` / `limit` 分页读取板条目；隐藏上下文给出相关摘要，完整正文按需获取。

## 存储、历史与指标

`super-agent/commit.json` 先同步写入，再更新兼容的 `state.json`；读取选择修订号最高的有效副本，旧文件和可选字段仍兼容。`events.jsonl` 仅记录观察索引，达到 8 MB 后转入 `history/`；操作明细在达到归档阈值时保存已结算历史。

历史清理先保存归档，再删除符合条件的目标、任务、计划、产物与操作记录；当前工作、未知操作、依赖、产物消费者和核验关系受保护。达到任务或目标容量上限会要求归档，避免静默丢弃历史。当前是便携文件存储；多个独立服务实例共同调度同一目录需要另外实现跨进程事务和租约。

面板显示实际观察到的模型轮次、工具调用、重试及续做次数；状态另保存停滞、提交任务计数、已结算轮次执行时间和初次排队时间。未接入实际模型 usage 和计费数据，不能把这些计数当作 token、费用或效率收益证明。确定性调度回归不代替真实供应商、真实容器和长时间任务基准测试。
