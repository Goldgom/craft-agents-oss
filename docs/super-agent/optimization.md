# 超级智能体实现审查与优化建议

## 1. 审查结论

审查日期：2026-10-04。范围为当前源码；本机历史运行记录用作案例，不代表当前已安装程序已更新。

当前已经实现持久节点会话、节点内串行、跨节点并行、真实完成事件、工具权限、计划版本、链边界续接和后台自检。原审查发现的四项可靠性缺陷现已修复，新增完整回复动作解析、关联脚本结果交付确认、运行存活对账及持久动作回执。下一步应提高**可执行任务补位和证据验收**，优化主节点协调成本及节点选择。

三个重点：

| 方向 | 主要缺口 | 优化目标 |
| --- | --- | --- |
| 工作效率 | 主模型承担大量逐条协调，选择器只看队列条数，计划难以表达并行依赖 | 就绪任务自动分配，合并无须单独决策的消息，减少等待和重复上下文 |
| 工作持续性 | 已补运行存活对账和失败回执；就绪任务补位、进展诊断及目标预算仍依赖主节点 | 从事件、任务依赖和检查点持续推进，发现无进展并作出明确处理 |
| 工作质量 | 已关联脚本运行与交付；通用验收证据和产物版本仍主要是自由文本 | 每个成果带版本和验证证据，关联执行成功后才验收完成 |

- 一个节点只运行一个轮次，不同节点可以并行；团队不存在“两节点上限”。

- 主节点遇版本冲突时，在原链预算内获得协调轮次。
- 本轮失败或没有新回复时不重放历史回复及动作。
- 工作节点提交后，计划仍等待主节点核验；任务提交与目标完成已有区分。
- 重启后不自动重放已经开始且可能产生副作用的任务。
- 脚本记录退出码、hash、超时和进程树停止结果，状态无法确认时使用 `untracked`。
- 脚本终态绑定运行、任务和计划，直接交主节点，并在正常完成结果轮次后确认交付。
- 长回复的控制块从完整文本解析，显示文字与动作正文分别限长；协议失败记录明确回执。
- 运行中核对宿主存活，保留真实忙碌和不确定状态；确认停止后不重放任务副作用。
- 工作节点与主节点动作回执持久化，实际目标 ID、已应用、被拒绝及未尝试部分对用户可见。
- 上下文已经按节点精简；底层提供商及当前历史管理功能已有压缩能力。

历史上的通信链和共享板报错仍说明这两类问题需要关注，但不能据此把当前新增的续链及协调机制判定为不存在。

## 3. 历史发现的四项可靠性问题与已修复行为

本节的缺陷描述及复现结果记录修复前行为；“已修复行为”描述当前工作区实现。后续扩展建议单独列出。

### 3.1 已修复：长回复静默丢失派工

**修复前问题**：`finishTurn()` 先把整个 `finalText` 截到 64000 字符，然后查找动作块；被截掉或截断的控制块可能没有产生派工，也没有协议错误。这会造成“回复说继续安排，实际没有任务”。

修复前隔离复现：

| 输入 | 实际派出任务 | 错误记录 |
| --- | --- | --- |
| 131 字符，含完整末尾动作块 | 1 | 无 |
| 65126 字符，动作块位于截断点之后 | 0 | 无 |
| 64096 字符，动作块跨截断点 | 0 | 无 |

**已修复行为**：

- 从完整、未截断回复解析单个末尾控制块，显示文字限制 64,000 字符，动作正文独立限制 256,000 字符。
- Markdown 围栏中的动作示例保留为代码，不执行、不在最终显示文字中过滤掉。
- 非准确标签、未闭合、嵌套、多块、控制块之后有正文或超限，均产生明确协议拒绝；JSON 和动作 schema 继续严格校验。
- 主节点可在原链预算内修复协议或版本错误；真实执行结果进入动作回执。

实现与回归：[SuperAgentActions.ts](../../packages/server-core/src/super-agent/SuperAgentActions.ts)、[SuperAgentActions.test.ts](../../packages/server-core/src/super-agent/SuperAgentActions.test.ts)。后续仍可把派工迁到宿主结构化工具，减少文本协议的维护成本。

### 3.2 已修复：异步脚本终态缺少可靠交付和计划关联

**修复前问题**：模型任务提交后异步脚本仍可能运行，但计划关闭只检查任务状态；脚本终态先通知工作节点，缺少运行、任务与计划的关联，上报主节点还可能被通信链限制拒绝。

修复前隔离执行器复现的状态顺序：

```text
工作节点启动脚本：task=completed，script=running
主节点关闭计划：plan=completed，script=running
脚本退出码 1：script=failed
工作节点上报失败：通信链限制拒绝
最终：task=completed，plan=completed，script=failed，主节点没有新增处理轮次
```

**已修复行为**：

- 每次受管执行分配 `runId`，任务动作启动的运行绑定 `taskId / planId`。
- 成功、失败、停止、无法确认停止及绑定任务的启动失败，直接以系统结果轮次交主节点，携带 `scriptRunId`，不重复结算原工作任务。
- 队列满时保留 `resultPending`，释放空位后补交。入队记录 `resultQueuedAt`，主节点结果轮次正常完成才设置 `resultReportedAt`。
- 发送失败、丢失完成事件及重启中断时保留结果，最多自动投递 3 次；达到上限后记录错误并等待显式继续或巡检。用户取消暂停相应结果的自动补交。
- 关联脚本仍运行、状态未知或结果尚未确认时不能关闭计划；失败或停止的关联脚本阻止计划完成。投递重试不启动新脚本。
- 文件监测和历史清理保留待核验的执行证据；单项任务取消按运行 ID 移除关联核验轮次，保留其他主节点工作。

实现与回归：[SuperAgentService.ts](../../packages/server-core/src/super-agent/SuperAgentService.ts)、[SuperAgentScriptResults.test.ts](../../packages/server-core/src/super-agent/SuperAgentScriptResults.test.ts)。脚本成功和结果交付确认仍需结合实际产物进行计划验收；后续可以增加明确的验收证据和执行重要性声明。

### 3.3 已修复：丢失完成事件后运行状态长期挂起

**修复前问题**：运行中的 `tick()` 缺少已开始轮次与真实会话状态对账，`working` 和未结束轮次又阻止全队空闲自检。丢失完成事件的内存探针在时间推进 24 小时后仍保留挂起轮次。

**已修复行为**：

- 每秒核对已开始轮次的实际宿主状态，启动先留 10 秒宽限，随后至少间隔 1 秒的两次停止检查才补齐错误。
- 第一次停止观察让已排队的正常完成事件先结算；仍在处理的长任务、权限等待及宿主查询失败保留原状态。
- 确认停止时结果标记未知、任务失败、计划受阻，并安排主节点检查；通信链耗尽仍可交付诊断。
- 解除异常旧会话绑定，晚到或重复终态不能串入后续新会话任务。保留原会话与产物供人工或主节点核验，不读取历史最终回复、不自动重放任务。
- 普通主节点核验轮次本身失败时不自循环；脚本结果轮次沿用最多 3 次的投递预算。

实现与回归：[SuperAgentService.ts](../../packages/server-core/src/super-agent/SuperAgentService.ts)、[SuperAgentLiveness.test.ts](../../packages/server-core/src/super-agent/SuperAgentLiveness.test.ts)。后续可增加事件时间、进展诊断及后端健康指标；单纯运行耗时不作为失败依据。

### 3.4 已修复：动作失败未进入主节点任务回执

**修复前问题**：工作节点模型正常结束后，即使共享板更新等动作被拒绝，给主节点的任务总结仍可能只有模型“已更新”的声明。隔离探针中任务完成、共享板保留旧内容，主节点未收到版本拒绝。

**已修复行为**：

- `SuperAgentActionReceipt` 持久化本轮控制结果，总体为 `applied / rejected / partially_applied`。
- 保存逐项动作 ID、类型及真实目标 ID，列出已应用动作、拒绝原因和后续未尝试动作 `notAttempted`。
- 工作节点回执随任务结果交主节点；主节点无工作任务的聊天轮次也将回执存入结果消息。
- 错误通知来源节点、主节点与用户；协调提示要求检查真实回执及最新状态，只处理未成功部分。
- 保留已经产生的任务结果和前序成功动作，分别检查产物质量与控制动作执行结果。

实现与回归：[types.ts](../../packages/shared/src/super-agent/types.ts)、[SuperAgentActionReceipts.test.ts](../../packages/server-core/src/super-agent/SuperAgentActionReceipts.test.ts)。回执记录控制动作的实际结果；外部副作用的幂等、检查点和验证仍需要下一步完善。

## 4. 提高工作持续性

### 4.1 把任务补位与空闲复盘分别调度

当前持续工作自检的语义是“全队连续空闲 30 分钟”。任意排队轮次、运行节点、待授权或运行/未知脚本都会阻止它。这适合空闲复盘，但不能及时补充已有计划中的可执行任务。

建议：

1. 任务结果、依赖满足、节点空闲、授权结果及连接恢复触发计划协调。
2. 宿主确定性检查就绪任务和可用节点，已授权就绪任务自动补位。
3. 只有确实需要判断、拆分或调整计划时唤醒主模型。
4. 30 分钟机制保留用于查遗漏、复盘和重新评估受阻目标。
5. `untracked` 优先阻止关联计划和资源的执行；无依赖的其他工作可继续，前提是资源关系明确。

初轮动作最多 4 个任务，主节点完成初轮后自身没有关联任务时不会自动获得继续派工轮次；其他 worker 忙碌又会阻止空闲自检。大团队因此可能首批工作期间长期保留空闲节点。应由就绪队列和依赖满足事件推动补位。

### 4.2 在已保存回执之上完善幂等与检查点

当前动作按计划、共享板、任务、消息、脚本顺序执行，可能部分成功；已保存真实回执和未尝试动作，协议、JSON、schema 及主节点版本冲突具备原链预算内协调。普通业务错误和工作节点冲突交主节点判断，仍缺少统一检查点及通用动作幂等处理。

建议在现有逐项动作 ID 和 `applied / rejected / notAttempted` 记录基础上，增加跨重试的 `idempotencyKey`、状态版本与执行检查点，减少恢复时对自然语言判断的依赖。

- 纯状态动作先完成引用、版本和容量预检，再提交。
- 外部副作用放入持久执行队列，幂等消费，不能假定可以回滚。
- 已成功动作不重放，失败部分进入有次数限制的协调轮次。
- 主聊天和进度展示必要的派工拒绝，避免仅存在于内部节点消息。

### 4.3 根据进展和错误类型恢复

新阶段可以开启新通信链，因此链内 32 轮限制不等于一个目标的总预算。建议给目标或计划独立记录调用、token、费用、耗时和返工预算。

对错误分类：连接/限流可有界退避；输入或动作错误要求修正；权限和真实依赖未满足进入明确等待状态；已经发生副作用的中断任务读取检查点后恢复。

记录已验证产物版本、通过的检查和剩余验收项，形成进展指纹。同样错误或同样结果反复出现且没有新证据时，降频、升级诊断或记录具体阻碍。长期有实际进展的任务继续运行。

没有目标或没有可执行变化时，可延长自检间隔，收到新用户请求或外部状态变化立即恢复，减少固定频率的空转。

## 5. 提高节点组工作效率

### 5.1 用任务依赖图表达并行工作

当前一个计划只允许一个排队或运行任务，依赖和写入范围主要在自然语言中。建议形成：

```mermaid
flowchart LR
    G[用户目标及预算] --> P[主节点拆分和调整计划]
    P --> D[任务依赖图与资源声明]
    D --> Q[就绪队列]
    Q --> S[能力和负载选择器]
    S --> W[持久工作节点]
    W --> E[产物及执行证据]
    E --> V[自动检查与选择性独立核验]
    V --> D
    V --> C[验收完成或返工]
```

任务增加 `dependsOn`、所需能力、输入产物版本、输出约定及读写资源声明。一个目标可以包含多个并行子任务，执行并发由节点、依赖、连接额度及资源冲突控制。

并行写入需要独立目录、工作副本或明确写锁；验证使用固定版本产物。依赖只有在要求的提交或验收条件满足后才释放，避免读取尚在修改的文件。

逐步增加任务图支持即可，当前计划接口和串行队列可继续作为兼容入口。

### 5.2 改善节点选择

[addTask()](../../packages/server-core/src/super-agent/SuperAgentService.ts) 未指定节点时只按待处理轮次数选择，同负载按配置顺序。它不包含实际预计等待、执行时长和验收成功率。固定提示词示例还使用第一个 worker ID，存在选择偏置风险；不能仅据此解释历史的全部分工。

建议先做可解释的简单选择器：

1. 按数据源、工具、能力和健康状态筛选。
2. 比较节点最早可开始时间和预计任务时长。
3. 优先符合任务类型且最近验收稳定的节点。
4. 同条件轮转选择；显式指定节点仍有效。
5. 在主节点上下文中提供队列数量、最早可启动时间、健康状态及分派理由。

实际平均时长和成功率应从同类任务积累，初期用保守默认值。涉及共享模型连接的节点还需要连接级 RPM、TPM 和并发控制，防止多个节点各自限速却共同触发限流。

### 5.3 合并协调，减少主节点排队

当前每个结果、消息、广播接收者、权限说明都可能消耗独立模型轮次。团队越大，主节点需要处理的相近总结越多。

建议消息分为进展、结果、请求、阻碍和决策：普通进展更新状态；需要判断的消息才唤醒模型。同计划短时间内的多个结果可在 0.5～2 秒窗口内合并处理，紧急阻碍和用户请求立即处理。

增加 inbox 游标、去重键和已处理事件集合。合并保留任务来源、事件顺序及通信预算，不能遗漏单个结果或重新传播已处理消息。主节点队列增加等待老化机制，持续用户对话期间也给验收协调适当执行机会。

### 5.4 保留会话与稳定上下文

当前保存配置时比较完整节点对象，头像、评分或限速变化也可能重置 runtime，下一次创建新隐藏会话。建议将配置分为展示/调度、提示词、执行身份三类；前两类尽量保留会话，模型、连接及环境变化才按策略交接。

脚本关键词还会影响系统提示词，宿主提示词变化时可能销毁模型运行时。建议保持核心职责与协议稳定，将本轮脚本信息放在任务上下文。这样仍可保留精简提示，但减少运行时重建。

当前摘要只提供有限任务、计划和共享板。补充按 ID 查询完整内容、状态过滤和分页工具，标注摘要完整性。共享条目增加计划、任务和产物关联，按任务相关性取信息；自然语言验收条件被截取时可读取完整版本。

### 5.5 缩短状态锁内的读取工作

[GET](../../packages/server-core/src/super-agent/SuperAgentService.ts) 在工作区串行锁内创建快照，快照还等待环境检查。Docker 健康探测缓存过期后，`info` 最长等待 10 秒，可能拖延同工作区派工和停止。这是锁范围上的风险，尚未做延迟压测。

环境健康探测改为独立异步缓存，快照只读缓存；实际启动时仍验证当前环境。历史分页、配置按版本缓存、实时活动增量传输。先测量序列化和磁盘成本，再决定是否把整文件状态改为事务存储或事件日志。

## 6. 提高工作质量

### 6.1 为验收建立结构化记录

当前已有主节点核验提示和计划状态分离，但 [任务与计划类型](../../packages/shared/src/super-agent/types.ts) 的产物和验收结果主要保存自由文本，无固定证据字段。建议在现有状态之外增加兼容的验收记录，逐步表达：

```text
submitted → verifying → accepted
                      → rework / blocked
```

验收记录包括：条件 ID、产物路径和 hash、执行命令和退出码、报告路径、实际覆盖和未覆盖项、核验节点、时间和结论。

不同任务使用对应检查：编程看构建/测试及变更范围；数据处理看计数、单位、约束和复算；文档看来源与关键事实；硬件看冻结版本、参考比对、覆盖及报告阶段。文件存在、退出码 0 或模型声称完成不能单独替代这些条件。

### 6.2 根据复杂度选择独立核验

实现者提供自测证据，重要成果交不同节点基于固定产物独立核验。普通可逆小任务优先使用确定性检查；复杂任务或首次失败后增加独立模型审查。

独立核验应读取完整约定和产物，实际运行可复算检查。若只复述实现者的总结，增加调用数却没有提高可验证质量。

### 6.3 设置输入与输出版本

任务声明输入产物的 revision/hash，结果声明输出产物版本。验收证据关联同一版本；实现修改后旧证据标记需要重新检查。已验收产物保留清晰的版本和产物索引，防止把旧快照、新源码及旧报告混在同一完成结论中。

### 6.4 让页面表达真实状态

区分“已排队”“运行中”“已提交”“验证中”“已验收”和“需返工”。主节点回复引用实际动作回执，动作拒绝说明真实原因和修复状态。

任务进度和目标验收进度分别展示。节点 working 状态旁可显示最近事件时间及具体等待原因，后台异常进入结构日志和团队健康状态，避免空 catch 隐藏存储或调度错误。

## 7. 节点分工示例

对原 ASIC 类开发任务，可以按以下工作线拆分，再根据依赖释放任务：

| 工作线 | 输出 | 主要依赖 |
| --- | --- | --- |
| 规格与数值约定 | 冻结接口、数值契约、完成条件 | 用户目标及已有资料 |
| RTL 实现 | 可构建源码、自测结果、版本清单 | 规格基线 |
| 独立参考模型 | 独立向量、黄金结果和差异检查 | 数值契约 |
| 接口与异常验证 | 背压、CRC、复位、边界场景结果 | 接口基线及可运行 RTL |
| 综合与时序分析 | 固定版本资源、时序及瓶颈报告 | 可综合 RTL |
| 交付与实现成本核验 | 证据索引、预算核算、未完成项 | 对应成果和报告 |

主节点处理规格取舍、关键失败、阶段验收和用户汇报。对独立准备工作可并行；对相同文件的修改或依赖未满足的验证保持有序。团队使用率由有效工作和资源条件决定。

## 8. 衡量优化效果

当前会话宿主已有 token 使用数据，超级智能体层还需将其按轮次差额关联任务和计划，避免把累计会话数据重复计费。

| 指标 | 用途 |
| --- | --- |
| 目标完成时间、首次验收通过率 | 同时衡量速度与质量 |
| 就绪到启动等待、提交到验收等待 | 判断节点空闲、限速和主节点瓶颈 |
| 每个验收成果的模型轮次、token、实际费用 | 判断分工及上下文是否节省成本 |
| 主节点协调占比、工作节点有效执行占比 | 判断消息和总结是否挤占产出 |
| 协议拒绝、重复派工、返工和冲突修复次数 | 判断可靠性及失败恢复 |
| 无进展持续时间、事件丢失补偿时间 | 判断持续性 |
| 同时运行任务和资源冲突等待 | 判断并发规模是否合理 |

使用同一任务、同一冻结输入和相同验收条件，对比单工作节点、两个工作节点及多工作节点。记录真实提供商、环境和上下文差异，报告延迟及成本分布；本次审查不预估百分比收益。
